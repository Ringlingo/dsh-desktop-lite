## 0. 一句话

**"双击解压即用"在本版壳下不可能成立**，原因是两条互斥约束：

```
data/ 里的镜像/投影   ┌─ 用【链接】(junction) ─→ 受限环境下建不了（EPERM）        ✗
                      └─ 用【真实目录】       ─→ 壳内嵌自检判为「物化」并移出       ✗
```

**两条路都被堵死 ⇒ 必须改壳内嵌的自检（只有厂商能重编）。** 缺陷不在壳的业务代码，在这个互斥约束上 —— 这也解释了为什么连续三个版本（healthfix / update-toast / lexical-diag）都没修好。

## 1. 根因链（完整、有据）

```
① 整包经 ZIP / 跨盘复制 → 421 条 junction 被摊平成真实目录
        ↓
② 壳内自检判「物化 421」→ 全部移出到 _backup/            （design 如此，交给 dsh 重建）
        ↓
③ 自检要重建的关键链接只有 2 条：C 段的两个外挂插件入口

        ↓
④ unrepairable = 2 → ok=false → Startup blocked
```

而 dsh 自己也走同样的路：`healProfilesModuleFallback` → `ensureSymlink` → `symlinkSync(..., 'junction')` → **同样 EPERM**（2026-09-15 实测）。

## 2. 关键机制（读 `dsh-app-boot/lib/index.js` 得出）

### 2.1 镜像条目的**两种合法形态**（同一套校验代码）

`moduleFallbackEntryCurrent(modulesDir, entry)`（`index.js:744-747`）：

```js
if (entry.kind === "symlink") return stat.isSymbolicLink() && readlinkSync(link) === entry.packageDir;
if (!stat.isDirectory()) return false;                      // ← 真实目录也可以
const existing = readModuleProxyRecord(link);
return existing?.version === entry.version
    && JSON.stringify(existing.dsh?.moduleFallback?.targets) === JSON.stringify(entry.targets)
    && Object.keys(entry.targets).every((_, i) => existsSync(join(link, `entry-${i}.js`)));
```

### 2.2 形态由**一处三元判断**决定（`index.js:720`）

```js
entries: !materialize ? [] : !isPackagedExecutable()
  ? [...links].map(([packageName, packageDir]) => ({ kind: "symlink", packageName, packageDir }))
  : [...links].flatMap(([packageName, packageDir]) => {
      const source = packageProxySource(packageName, packageDir);
      return Object.keys(source.targets).length === 0 ? [] : [{
        kind: "proxy", packageName, version: source.version, targets: source.targets
      }];
    }),
```

- `isPackagedExecutable()` = `process.pkg !== void 0`
- **普通 Node（我们的情况）⇒ `symlink`**；pkg 打包可执行 ⇒ **`proxy`（真实目录 + `entry-N.js`）**
- 源码注释点明设计意图：*"Plain Node writes symlinks; **a packaged executable writes ESM proxies** … because operating-system links cannot enter pkg's virtual filesystem."*

**⇒ 只要让这处判断走 `proxy` 分支，镜像就变成真实目录 ⇒ 不需要建链接能力。** 而且 proxy 里的 `targets` 是**绝对 file:// URL**，换路径后与重新算出的 `targets` 不匹配 ⇒ `moduleFallbackCurrent` = false ⇒ dsh **就地重写** proxy 目录（写目录，任何进程都能做）⇒ **换机/换路径自适应**。这是"解压即用"想要的语义。

### 2.3 profile 级链接（C 段那两条）走另一条路

`healProfileModuleFallback`（`index.js:897-903`）为每个 bundle 建**两条** junction：

```js
ensureSymlink(ownedLink, target);            // <profile>/.dsh-module-fallback/node_modules/<pkg>
ensureProfileSymlink(profileLink, ownedLink);// <profile>/node_modules/<pkg>   ← 仅在 ENOENT 时创建
```

⇒ 与 A 镜像无关，必须单独处置（见 S2b）。

## 3. 修复方案

### 3.1 厂商必须做的两件事（**只有厂商能编壳**）

#### S1 · 自检放行「dsh 托管的代理目录」（**这是"解压即用"的开关**）

自检当前对 `data/profiles/**` 下**任何真实目录**一律判「物化」并移出（`sweepLinksOnly` / `sweepDeclared`）。
必须改成：**真实目录 + 合法的 dsh 代理目录 = 正常**。

建议在 `scripts/startup-selfcheck.mjs` 里加一个共用判据，并在 A/B/C/D 四段的"物化"判定处改用它：

```js
/** 真实目录且是 dsh 托管的代理目录 ⇒ 合法，不是物化。 */
function isManagedProxy(p) {
  try {
    if (!fs.lstatSync(p).isDirectory()) return false;
    const m = JSON.parse(fs.readFileSync(path.join(p, 'package.json'), 'utf8'));
    const t = m?.dsh?.moduleFallback?.targets;
    if (t === undefined || t === null) return false;
    return Object.keys(t).every((_, i) => fs.existsSync(path.join(p, `entry-${i}.js`)));
  } catch { return false }
}
// 判定处：真实目录 && !isManagedProxy(x) 才算物化
```

**验收**：把 `data/profiles/node_modules/**` 全部换成代理目录形态后，自检报 `物化 0`、`ok=true`。

#### S2 · 把 A 镜像形态切到 proxy

改 `runtime/dsh/node_modules/@deepseek-ai/dsh-app-boot/lib/index.js` 的 `resolveModuleFallbackEntries`（约 720 行）：
**优先 proxy**（建议加环境开关，默认 proxy，便于回退）：

```js
const FORCE_PROXY = process.env.DSH_MODULE_FALLBACK !== 'symlink';
entries: !materialize ? [] : (FORCE_PROXY || isPackagedExecutable())
  ? [...links].flatMap(([packageName, packageDir]) => { /* 原 proxy 分支，保持不变 */ })
  : [...links].map(([packageName, packageDir]) => ({ kind: "symlink", packageName, packageDir })),
```

> ⚠️ **不要改 `symlink` 分支的语义**，只调**选择**；`healProfilesModuleFallbackLocked`、`moduleFallbackEntryCurrent`、`ensureModuleProxy` 都已原生支持 proxy，无需改动。
> ⚠️ **注意**：`packageProxySource` 对 `targets` 为空的包**会跳过**（不进镜像）。切换后必须核对 A 镜像条数是否仍满足启动（见 §4 验证矩阵 V2）。

#### S2b · 外挂插件**内置化**（消除 profile 级的两条必然 EPERM）

把两个插件实体从 `data/plugins/<pkg>` 放进**安装内** `runtime/dsh/node_modules/<pkg>`，并改 `data/profiles/web/package.json`：
- `bundles`：保留 `tabbit-browser`、`dsh-runtime-inspector`
- `dependencies`：**删掉那两条 `link:`**（它们不再是 link 依赖）

效果：
- 自检 C 段把它们归入「内置 bundle」⇒ 只校验**安装内可解析** ⇒ **零链接需求** ✓
- dsh 的 `installationPackageNames` 会包含它们 ⇒ `dependencyClosure` 的 filter 排除 ⇒ **不再创建 `ownedLink` / `profileLink`** ✓
- 副作用：A 镜像闭包会多出这两个包（及其依赖）⇒ **需重新 provision 一次**（条目数变化，见 V2）

> 若厂商不愿动安装目录，替代方案：保留 `link:`，但让 S1 的判据同样适用于 profile 级投影（即 profile 级的真实目录投影也放行）。**但插件是**被 Node 直接 import 的**，proxy 形态对它的 ESM 导出完整性有风险 —— 内置化更干净。**

**现状代价（实测）**：壳内嵌自检把 proxy 真实目录**判为「物化」并移出**：

（当时那"2 项"是插件只放在 profile、没放安装内造成的；两处都放后 `ok=true`。）

### 6.5 顺带发现的另一个壳缺陷（建议一并修）

**自检脚本写入失败时是 fail-closed**：把 `data/downloads/startup-selfcheck.mjs` 设为只读后再启动，壳直接阻断：

```
[selfcheck] ok=false 写入自检脚本失败：拒绝访问。 (os error 5)
Startup blocked by selfcheck
```

⇒ 这既堵死了一条"注入修复"的应急通道，也让**任何文件权限异常都会导致应用起不来**。
**建议改为 fail-open**：写不进去就用现存的那份（并提示版本可能不一致），只在**真的**修不好时才阻断。

## 10. 🔧 §9 之后仍报错 —— 真正的根因是「经典脚本被换成了 ESM」（2026-09-17）

### 10.1 现象

打完 §9 的补丁后，**boot 图已完整（57 项）**，但界面**依旧**报：
`client-modules: HTML did not preload @deepseek-ai/dsh-client-modules/client.js`

⇒ 说明问题不在"图里有没有它"，而在"**它被加载后能不能注册**"。

### 10.2 根因（决定性证据）

列出 head 内全部标签后，第 3 个标签其实**在**：

```html
<script src="/plugins/??@deepseek-ai/dsh-client-modules/client.js&amp;rev=78b1463854f3"></script>
<!-- 注意：无 type="module" ⇒ 会被浏览器当【经典脚本】执行 -->
```

该 URL 返回 **HTTP 200**，但内容是**我生成的 proxy 入口文件**：

```js
export * from "file:///…/@deepseek-ai/dsh-client-modules/lib/client.js"
import * as target from "file:///…"
export default target.default          ← 经典脚本里出现 export = 语法错误 ⇒ 整段不执行
```

对比真实的 `lib/client.js`（20,814 B）：

```js
window.__ModuleLoader__.load({        ← 这才是「注册」：把 factory 推进 pendingQueue
  id: "@deepseek-ai/dsh-client-modules",
  factory: (require) => { … }
})
```

**⇒ 链条**：`./client` 入口被写成 **ESM 再导出** → 经典 `<script src>` 加载它 → **SyntaxError** → 永不执行 → `pendingQueue` 里没有它 → `__ModuleLoader__.create()` 抛
`HTML did not preload …/client.js` ✓✓ 与报错逐字吻合。

**为什么 `bootInjections` 用经典脚本？** 源码（`dsh-client-modules/lib/index.js:430-438`）：

```js
for (const batch of application) rows.push({ kind: "script-preload", src: batch.url });
for (const batch of bootstrap)   rows.push({ kind: "script-src", placement: "head", src: batch.url });
```

⇒ **bootstrap 批是 `<script src>`（经典脚本）**，application 批是 `preload as="script"` 后同样以经典脚本执行 —— 也就是说 **`/plugins/??<pkg>/client.js` 的契约就是"可被经典脚本直接执行"**，而 proxy 的 ESM 再导出**天然违反**这个契约。

### 10.3 修法（第 4 处补丁，同一文件）

```diff
 	for (const [index, target] of Object.values(targets).entries()) {
 		const specifier = JSON.stringify(target);
+		if (Object.keys(targets)[index] === "./client") {
+			/* 浏览器半边是经典脚本（window.__ModuleLoader__.load 注册），
+			   由 /plugins/??<pkg>/client.js 路由以 <script src> 直接执行。
+			   若写成 ESM 再导出，经典脚本会因 export 语法错误不执行 ⇒ 永不注册 ⇒
+			   报 "HTML did not preload …/client.js"。故原样复制真实文件内容。 */
+			try { writeFileSync(join(link, `entry-${index}.js`), readFileSync(new URL(target))); continue; } catch {}
+		}
 		writeFileSync(join(link, `entry-${index}.js`), `export * from ${specifier}…`);
 	}
```

> 只对 **`./client` 子路径**做复制（其余子路径仍是 ESM 再导出 —— 那些是**真模块**，复制会破坏其相对 import）。
> 同样需要**强制重建镜像**（`moduleFallbackEntryCurrent` 只看 `entry-N.js` 存在性）。

### 10.5 教训（比 §9 更本质）

**「客户端半边」这类产物不是普通模块，而是"被当作经典脚本执行的注册片段"。**

## 14. 🔧 `dsh-runtime-inspector` 报「读不到 runtime/runtimes.json」（2026-09-17）

### 14.1 报错

```
内置运行时出问题了读不到 runtime/runtimes.json：
ENOENT: no such file or directory, open 'D:\AI\dsh-desktop-lite\data\profiles\runtime\runtimes.json'。
请先运行 provision-runtimes.mjs 落地内置运行时。
```

### 14.2 根因（**§6 S2b 的第二个隐性副作用**）

插件 `data/plugins/dsh-runtime-inspector/lib/index.js` 用**相对层数**推应用根目录：

```js
const HERE = path.dirname(fileURLToPath(import.meta.url))   // …/dsh-runtime-inspector/lib
/** lib → 插件目录 → plugins → data → 应用根目录 */
const ROOT = path.resolve(HERE, '..', '..', '..', '..')
const MANIFEST = path.join(ROOT, 'runtime', 'runtimes.json')
```

这个推导**只在插件位于 `<root>/data/plugins/<pkg>/lib` 时成立**。实测三处位置的结果：

| 插件位置 | 上溯 4 层得到 | 找 `runtime/runtimes.json` |
| --- | --- | --- |
| `data\plugins\<pkg>\lib`（原设计） | `<root>` | ✅ |
| **`data\profiles\web\node_modules\<pkg>\lib`**（S2b 为 Node 解析链放置） | `<root>\data\profiles` | ❌ **就是报错那条** |
| `runtime\dsh\node_modules\<pkg>\lib`（为自检 inbox 放置） | `<root>\runtime` | ❌ |

⇒ **把插件实体搬到别处，就打破了它"按层数推根"的假设。**

### 14.3 修法（三处副本一起改）

把 `ROOT` 换成**分层解析**（可靠性优先，保留原逻辑作最后兜底）：

```js
function resolveRoot() {
  // ① 壳拉起 dsh 时必然有 DSH_HOME=<root>/data ⇒ 取其父目录
  const home = process.env.DSH_HOME
  if (typeof home === 'string' && home.length > 0) {
    const parent = path.dirname(path.resolve(home))
    if (fs.existsSync(path.join(parent, 'runtime'))) return parent
  }
  // ② 自下而上找同时含 runtime/ 与 data/ 的目录
  let dir = HERE
  for (let i = 0; i < 8; i += 1) {
    const next = path.dirname(dir); if (next === dir) break; dir = next
    if (fs.existsSync(path.join(dir, 'runtime')) && fs.existsSync(path.join(dir, 'data'))) return dir
  }
  // ③ 退回原来的上溯 4 层
  return path.resolve(HERE, '..', '..', '..', '..')
}
```

**改动位置（3 个副本）**：`data\plugins\…\lib\index.js` · `data\profiles\web\node_modules\…\lib\index.js` · `runtime\dsh\node_modules\…\lib\index.js`
（各自备份为 `index.js.prefix.bak`）
